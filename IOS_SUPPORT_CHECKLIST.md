## Verdict

**This is not a rewrite — it is a configuration + credentials job.**

The app is on Expo **managed workflow / CNG** (there is no `ios/` or `android/`
folder), so the iOS project is generated by prebuild. The JS is already
iOS-aware: ~50 `Platform.OS === "ios"` branches exist for keyboard avoidance,
date pickers and padding, and every Android-only API (`ToastAndroid`,
notification channels, `StatusBar.currentHeight`) is correctly guarded.

## B. `app.json` changes — 8 items

### B1. Fix the Google Sign-In plugin — **BLOCKING, prebuild fails without it**

Currently listed as a bare string on line 39. On iOS this plugin **requires**
an `iosUrlScheme` argument or `expo prebuild` throws.

```jsonc
// BEFORE
"@react-native-google-signin/google-signin",

// AFTER
["@react-native-google-signin/google-signin", {
  "iosUrlScheme": "com.googleusercontent.apps.943646523727-XXXXXXXX"
}]
```

Use the **reversed** iOS client ID from A5.

### B2. Add an iOS block to `expo-build-properties` — **BLOCKING for dev builds**

The plugin currently has only an `android` key. `usesCleartextTraffic` is
Android-only and does nothing on iOS. The dev API URL is
`http://<lan-ip>:3003` (`src/api/api.ts:29`), which iOS **App Transport
Security blocks outright**.

```jsonc
["expo-build-properties", {
  "android": { /* …unchanged… */ },
  "ios": { "deploymentTarget": "15.1" }
}]
```

…plus the ATS exception in B3. Production (`https://chalokhelne.com`) is
unaffected — this only breaks the `local` and `development` profiles.

### B3. Add the required `ios.infoPlist` keys

Existing keys (`UIBackgroundModes`, `ITSAppUsesNonExemptEncryption`) are
correct — keep them and add:

```jsonc
"NSLocalNetworkUsageDescription": "Allow Chalo Khelne to connect to the local development server.",
"NSAppTransportSecurity": { "NSAllowsLocalNetworking": true }
```

> Ship the ATS exception in **dev/preview profiles only**. Do not submit a
> production build with a blanket `NSAllowsArbitraryLoads` — Apple asks for
> written justification.

### B4. Declare `expo-image-picker` in `plugins` — **review-rejection risk**

`ImagePicker` is used in at least 5 screens (`ChatConversationScreen`,
`EditPlayerProfileScreen`, `PlayerPaymentScreen`, `SellUploadImages`,
`SocialScreen`) but the plugin is **not** in the `plugins` array, so iOS gets
no explicit camera / photo-library usage strings. Apple rejects missing or
generic ones.

```jsonc
["expo-image-picker", {
  "photosPermission": "Allow Chalo Khelne to access your photos to upload profile pictures, posts and payment screenshots.",
  "cameraPermission": "Allow Chalo Khelne to use the camera to take photos for your profile and posts."
}]
```

### B5. Set `ios.icon`

Point at the new 1024×1024 PNG from E1. iOS must not inherit the current
`./assets/splash-icon.jpg`.

### B6. Decide on `supportsTablet`

Currently `true`. That tells Apple to **review the app on an iPad** — iPad
layout defects are a very common rejection cause. Unless the layouts have been
tested at iPad width, set it to `false`.

### B7. Remove or justify the `expo-media-library` plugin

The plugin declares *"Allow Chalo Khelne to save QR codes to your gallery"*,
but `MediaLibrary` is **never imported anywhere in `src/`** — only
`ImagePicker.requestMediaLibraryPermissionsAsync()`. Declaring an unused
permission invites reviewer questions. Either drop the plugin + dependency, or
actually implement QR saving and add `savePhotosPermission`.

### B8. Add `ios.buildNumber` handling

There is no `buildNumber` and no iOS `autoIncrement`. The **first** submission
will work; every one after it is rejected as a duplicate build number. Handled
together with C3.

### D2. Replace hardcoded notch padding with safe-area insets — ✅ done

> **Correction to the original survey.** It listed 9 sites. On inspection only
> **5 were real**. The three
> `paddingTop: Platform.OS === "android" ? StatusBar.currentHeight : 0` sites
> (`InvitationsScreen.js:690`, `InvitePlayerScreen.js:845`,
> `NotificationsScreen.js:186`) are **already correct** and were left alone:
> each screen wraps its content in `SafeAreaView` imported **from
> `react-native`**, which applies the safe area on iOS and is a no-op on
> Android. The Android-only `paddingTop` is exactly the right complement to
> that. Changing them would have double-padded iOS.

Fixed, each keeping Android **pixel-identical** (the old Android literal minus
a nominal 24pt status bar becomes the additive constant) while iOS now adapts
per device:

| Site | Was | Now |
|---|---|---|
| `RegisterScreen.js` `scrollView` | `ios ? 60 : 40` | `insets.top + 16` |
| `GroupChatListScreen.js` `header` | `ios ? 60 : 50` | `insets.top + 26` |
| `PlayerHomeScreen.js` `sidebarInner` | `ios ? 50 : 30` | `insets.top + 6` |
| `PlayerHomeScreen.js` `notificationHeader` | `ios ? 60 : 40` | `insets.top + 16` |
| `viewer/SocialScreen.js` `commentInputContainer` | `ios ? 35 : 15` | `Math.max(insets.bottom, 15)` |

The real bug the flat numbers caused: **iPhone SE** has a 20pt status bar, so a

Both `PlayerHomeScreen` panels are `position: absolute` overlays anchored to the

`ScreenHeader.tsx` was also fixed (flat `8` on iOS → `insets.top + 8`), but note

`App.js:80-110` builds tab-history tracking and double-press-to-exit on
`BackHandler.addEventListener("hardwareBackPress", …)`. **That listener never
fires on iOS.** `BackHandler.exitApp()` is also a no-op there — and Apple
forbids apps that quit themselves, so leaving it Android-gated is correct.

Static audit results:

- **Swipe-back is intact.** `gestureEnabled: false` appears exactly once, in
  `OnboardingNavigator.js:14`, which is intentional. Every other pushed screen
  keeps the iOS edge-swipe gesture.
- **40 of 119 screen files** have no `goBack()` / back-arrow / `pop()` call.
  Most are fine: tab roots (`PlayerHomeScreen`, `SocialScreen`, `HomeScreen`,
  `TrainerStaffHome`) and modals, which all carry a close affordance —
  `AddPopUp`, `DOBGateModal`, `FilterModal`, `SportSelectionModal`,
  `SportsModal`, `TeamTieScorerModal` were each checked and have one.
- ✅ **`NewsList` — fixed.** It was registered at `PlayerNavigator.js:522-526`
  with **both** `headerShown: false` **and** `tabBarStyle: { display: 'none' }`,
  and `NewsListScreen.js` had no back control of its own. On Android the
  hardware button covered it; **on iOS the only way out was the edge-swipe
  gesture**, which is not discoverable.

  Added a fixed header row — back arrow + "News" title — placed **above** the
  `ScrollView` so it never scrolls away, and inside the existing
  `SafeAreaView edges={["top"]}` so it needs no manual inset. The screen already
  had `navigation` and `Ionicons` in scope. Carries `accessibilityRole="button"`

- `FAQS`, `PrivacyPolicy`, `TermsConditions`, `LeaderboardScreen` also lack back

Everything else here needs a real device to judge, so it stays a Phase 2 item.

## E. Asset changes — 3 items

### E1. App icon — **BLOCKING** — ✅ done

`assets/splash-icon.jpg` was a **500×500 progressive JPEG**. Apple requires a
**1024×1024 PNG with no alpha channel**; App Store Connect rejects the upload
otherwise.

**Produced `assets/app-icon-1024.png`** — 1024×1024, RGB, no alpha, verified
with `file`. `ios.icon` points at it.

Two deliberate choices worth knowing about:

- **Source is `assets/notification.png`, not `splash-icon.jpg`.** Both hold the
  brand mark at 500×500, but `notification.png` is a clean **RGBA PNG** while
  `splash-icon.jpg` is a lossy progressive JPEG. Upscaling the PNG avoids
  baking JPEG ringing into the App Store icon. The mark is trimmed to its
  bounding box and re-centred at 80% of the canvas so it does not float in
  dead space.
- **The iOS icon is the CK monogram only — no wordmark.** Apple's HIG advises
  against text in app icons; at the 60pt home-screen size the "Chalo Khelne"
  wordmark renders as illegible mush. Android keeps the wordmark version
  (see the caveat below).

> **Ceiling on quality:** every brand raster in `assets/` tops out at 500×500.
> The 1024 icon is therefore a 2× upscale — clean, but not as crisp as a native
> 1024 export would be. **Ask your designer for the logo as SVG or a 1024px+
> PNG** and regenerate. `assets/logo.jpg` is 2000×2000 but is unrelated stock
> art (see below), so it is not a usable source.

### E2. iOS dark / tinted icon variants (optional) — ⬜ skipped

iOS 18 supports dark and tinted icon variants via `ios.icon` as an object.
Skipped deliberately: the app sets `userInterfaceStyle: "light"`, so a dark
variant buys nothing today. Revisit only if the app gains dark mode.

### E3. Splash screen — ✅ done

`splash.image` was the same 500×500 JPEG — and `PIL` confirmed it was
**progressive**, which is the format most likely to misbehave in native image
loaders. **Produced `assets/brand-1024.png`**: the same wordmark artwork at
1024×1024 as a baseline PNG.

The original note recommended "≥1242px wide". That was over-spec — with
`expo-splash-screen`, the image renders at `imageWidth` (default 200pt = 600px
at @3x), so 1024 is already oversampled. Going larger from a 500px source only
adds upscale blur without adding detail.

Both platforms now use this one PNG, so the splash is identical on iOS and
Android and the schema error is gone.

### E-extra. Android adaptive icon — ✅ done, approved 2026-08-24

**This one changes your live Android launcher icon** and was done on explicit
approval, not as a side effect of the iOS work.

Android composites an adaptive icon from a foreground layer over a background
colour, then masks the result to the launcher's shape (circle, squircle,
teardrop…) and crops to roughly the **centre 66%**. It also parallaxes the
foreground during animation, so anything near the edge can swing out of view.

The old foreground was the full **wordmark** logo, so the "Chalo Khelne" text
was already being clipped on every Android launcher — the icon had been
quietly broken, independently of iOS.

**Produced `assets/adaptive-foreground.png`:**

| Property | Value | Why |
|---|---|---|
| Canvas | 1024×1024 | Standard adaptive-icon source size |
| Mode | **RGBA, transparent background** | The launcher composites it over `backgroundColor: "#ffffff"` |
| Content | CK monogram, no wordmark | Text cannot survive the mask |
| Extent | 60% of canvas — measured at **59% of radius** from centre | Comfortably inside the 66% safe zone, with margin for parallax |

Verified: all four corners `alpha = 0`; brand orange `rgb(231,126,0)` and green
`rgb(2,133,99)` present at `alpha = 255`.

> The interior of the "C" is transparent in the source art, so it shows through
> to the white `backgroundColor` — which is exactly how the mark is drawn. That
> is intentional, not a missing fill.

Android and iOS now show the **same monogram**. `assets/brand-1024.png` (the
wordmark version) is still used for the splash screen on both platforms and for
the shared booking receipt, which is where the wordmark belongs.

**Not done — `monochromeImage`.** Android 13+ themed icons fall back to a
desaturated version of the foreground when the user enables them. A dedicated
single-colour silhouette would look better. Low priority; say so if you want it.

### E-extra-2. Android notification icon — ✅ done, approved 2026-08-24

Also Android-only and also pre-existing — found while auditing every asset
path in `app.json`.

`expo-notifications` was pointed at `assets/notification.png`, the **full-colour**
monogram. Android does not display notification icons in colour: since Lollipop
it **discards every channel except alpha**, silhouettes the shape and tints it
with the configured `color`. A fully-opaque colour source therefore renders as a
**solid white blob** in the status bar.

**Produced `assets/notification-icon.png`:** the mark's alpha channel filled with
pure white on a transparent canvas, 384×384 (the spec is 96×96 at xxxhdpi;
supplying 4× lets Expo downsample cleanly), mark inset to 85%.

Verified: **0 non-white opaque pixels**, corners `alpha = 0`. Rendered over dark
at 96 / 48 / 24 dp, it still reads as "CK" at the real status-bar size.

> Unchanged: `color: "#f4511e"`, the tint Android applies to the silhouette.
> Worth knowing that it is **not** the brand orange — the mark is
> `#e77e00`, this is a redder orange. Cosmetic, left alone as a deliberate
> brand-accent decision rather than a bug.

| **B1–B8** | All `app.json` config. |

**How to validate Phase 0 on Windows, for free:**

```bash
npx expo config --type introspect        # runs the iOS mods, prints the real Info.plist
npx expo-doctor                          # dependency + config sanity
npm run typecheck && npm run lint
```

> **Correction (2026-08-24).** An earlier draft of this document recommended
> `npx expo prebuild -p ios --no-install`. **That does not work on Windows** —
> the CLI skips the iOS platform entirely and exits 0, so it silently validates
> nothing. Do not use it as a gate.

`expo config --type introspect` is the replacement, and it is actually the
better tool: it *executes* the introspectable iOS mods and prints the resulting
`Info.plist` and entitlements as JSON, without generating a native project at

#### Two extra defects found and fixed during the run

Neither was in the original 27; both were pre-existing and would have bitten
on iOS.

1. **Deprecated notification handler.** `NotificationService.js` used
   `shouldShowAlert`, which `expo-notifications@0.32` marks `@deprecated` and
   ignores on iOS. Its replacements `shouldShowBanner` / `shouldShowList` are
   **required** fields in the type. Without them, notifications arriving while
   the app is open are delivered **silently on iOS**. Fixed.

2. **Missing native peer dependency.** `react-native-reanimated@4.1.6` requires
   `react-native-worklets`, which was resolving only transitively and was never
   declared. expo-doctor's warning is explicit: *"Your app may crash outside of
   Expo Go without this dependency."* Now declared as `~0.7.2`.

   Note the SDK 54 baseline names `0.5.1`, but reanimated 4.1.6 depends on
   `0.7.2` directly — pinning down would create the duplicate-native-module
   problem, so `react-native-worklets` is listed in `expo.install.exclude`.

3. **Duplicate native module.** `react-native-calendars` hard-pins
   `react-native-safe-area-context@4.5.0` as a direct dependency, nesting a
   second native copy beside the app's `5.6.2`. Native builds may contain only
   one version of a native module. Resolved with an `overrides` entry.
   ⚠️ **Re-test the calendar screens on Android** — this is the one change with
   real regression surface.

## What you cannot verify before purchasing

Be realistic about this. On **Windows with no Apple account**, you can write
and statically validate the changes, but you cannot *run* iOS. Specifically,
these stay unverified until Phase 1 completes:

- Whether Google Sign-In actually succeeds (the highest-risk item)
- Whether push notifications register and deliver
- Safe-area / notch rendering — **D2 cannot be finished blind**
- Share sheet, `expo-print`, `react-native-view-shot` output
- Socket.IO reconnect after backgrounding

**Expo Go is not a workaround here.** This app depends on `expo-dev-client`
and native modules absent from Expo Go — `@react-native-google-signin`,
and push notifications (removed from Expo Go in SDK 53, and
`NotificationService.js` already detects and skips this case). Expo Go on an
iPhone would fail on exactly the flows you most need to test.

Genuine options for iOS runtime access, cheapest first:

1. **Buy the $99 membership.** Given how much of the risk sits in
   "does Google Sign-In work", this is usually cheaper than the alternatives.
2. **Borrow a Mac** — an EAS simulator build (`"ios": { "simulator": true }`,
   item C1) needs **no signing and no paid account**, so it runs on any Mac's
   simulator. Good for layout and D2; the simulator cannot test push or camera.
3. **Cloud Mac** (MacStadium, MacinCloud) — typically costs more per month
   than the annual membership.
